现有系统是一套已能独立部署的布雷顿循环热力试算后端（TypeScript + NestJS，PostgreSQL 持久化，Docker Compose 一键构建启动）。调用方可以做理想循环、实际循环、压比区间扫描寻优，也可以一次提交多组工况做批量核算；每次单点核算和扫描都会把输入输出落库，之后能按条件查历史。现场计算是对的：示范算例、四状态点、比净功和热效率、扫描拐点、批量部分失败、材料上限只标注不截断，这些都工作正常。温度的约定是热力学温度，单位开尔文。

异常现象：单点或批量核算的现场响应看起来没问题，但把同一条记录从历史里读回来，四个状态点上的温度就对不上了。用示范那组参数打实际循环，现场返回进气状态点 300、压气机出口大约 660.7、涡轮入口 1400、排气大约 759.5；立刻去查历史，这条记录的 input 里进气温度仍是 300，部件结果里的进气温度和实际出口温度也仍是 300 和大约 660.7，唯独 output 里那四个状态点变成了大约 26.85、387.5、1126.85、486.3。净功、加热量、热效率、相对压力现场和历史一致，示范接口不写历史所以不受影响，扫描历史里没有这四个状态点、这条路径也正常。同一请求稳定复现。理想循环（两侧效率为 1）落库之后，状态点温度同样对不上。

复现（服务起来后）：向实际循环接口提交压比 12、进气 300、涡轮入口 1400、压气机效率 0.86、涡轮效率 0.90、比热比 1.4。现场进气状态点应是 300，压气机出口大约 660.7。随即按核算类型加压比 12 查历史：该条 input.ambientTemperature 仍为 300，但 output 里进气状态点温度约为 26.85、压气机出口约为 387.5，既对不上现场响应，也对不上同一条记录里部件结果的温度字段。把同一组参数作为批量里唯一一组再走一遍：批量的现场结果状态点仍是 300 / 660.7，历史里这条批量记录中成功组的状态点同样变成 26.85 / 387.5。

期望：历史快照里的状态点温度必须和现场响应相同，也必须和同一条记录 input 里的进气/涡轮入口温度、以及部件结果里的进气/出口温度用同一套热力学温度。修好后重跑上面的复现：单点历史里进气状态点应回到 300，压气机出口应与现场大约 660.7 对上，并与同条记录部件结果的进气/出口温度对齐；批量历史里成功组同样对齐。示范算例、扫描拐点、理想闭式、材料上限、非法入参和并发条数一律保持原样。补上能锁住「现场状态点温度与历史快照一致、且不与同条记录其他温度字段分叉」的自动化测试。技术栈仍为 TypeScript、Node.js 20、NestJS、PostgreSQL 16，用 Docker Compose 一条命令把服务与数据库一起构建启动。
